# Decisions

What was decided while building trail, and why. `design.md` describes how trail works; this file records the choices behind it, so they aren't reopened by accident. Add to it when a decision changes.

## Product

- **Goal:** replace plannotator and tuicr for reviewing git changes. In order of importance: a better diff, code navigation, a guided review that follows calls instead of files, then AI integration.
- **Frontend:** a Neovim plugin. A standalone TUI that opens Neovim on demand was considered after definition navigation clashed with a user's Neovim config. Opening definitions in a separate Neovim (below) solved that, so the plugin stays. The engine knows nothing about Neovim, so a TUI can still be added later as another client.
- **Review flow:** two levels. A paths screen lists the paths, the changes no test reaches, the changed test files and the hunks in no path; entering a path shows its tree on top and the diff below. Paths can be visited in any order, and progress is tracked per hunk, so work done in one path counts in every path.
- **Paths show the impact of a change (replacing connected groups):** a path starts at a changed function and shows everything that can reach it, up to the entry points (functions nothing in the repository calls), and everything it calls, through unchanged code. The first version only connected changed functions to each other, so a change reached through an unchanged function (`Handler` → `Service.Create` → `Store.Save`) split into separate paths and the reach of a change was invisible.
  - **Overlapping changes share a path:** when one changed function's impact reaches another changed function, they become one path. Separate paths per change would multiply on big PRs.
  - **The engine works out everything, the screen shows a little:** the walk goes all the way up and down, capped by a node limit and a time limit. The view opens a couple of levels deep and the reviewer expands further.
  - **A path reads from beginning to end.** It is laid out as one tree per entry point going down through the calls, not centered on the change. The tree through most changes comes first; each later tree stops where it reaches something already shown ("joins"), and still shows any change of its own before that point. Trees that only join are folded on big paths.
  - **A path opens showing only its changes and how they connect.** Each change sits under the change it is reached from, the unchanged functions the call goes through drawn as a dotted connector (`├┄● Store.Save  ┄2`) that `za` opens into a row each. A `▸ N functions` row for them was used before and added a row per link. Showing every function on the way, even stopping at the last change, made a real 109-change path 2005 functions deep and unreadable; a link through many functions is itself a sign two changes are only loosely related. A change reached again shows again under each caller (below), once per caller even when two routes reach it.
  - **Every function on the way is one key away (`a`).** It opens every dotted connector into its functions. Branches that lead to no change are not shown, in that view or any other: they were folded lines that were noise in a review; their code stays one key away (`K`, `gd`) from the function calling them.
  - **A function's calls are shown in the order its body makes them.** Children used to be ordered by how many changes sit below them, so a function called last could be read first. Now each function's callees follow their first call in its body (tree-sitter's calls, in source order), so the tree and the steps read like the code. Callees it doesn't call by name, such as a changed type reached through its users or a value it uses, come after, by changes below. Trees themselves still start with the one through most changes.
  - **Steps are the path's changed functions, in the order the trees show them.** Unchanged functions are reached by moving through the tree, with `K` to see their code. A change that belongs to another path shows as changed without being a step.
  - **Rows show short names.** A row reads `Store.Save`, not `internal/platform/storage/postgres.Store.Save`; long package folders made the tree unreadable. Chosen over showing only the last folder (`postgres.Store.Save`) and over shortened folders (`i/p/s/postgres`). The engine sends `package` and `short` with each node so the plugin doesn't split names by language. The package used to sit in a column on the right; it is now among the cursor row's details (below).
  - **AI-proposed paths come later,** on top of this graph rather than instead of it.
- **Tests stay out of the trees:** a test calling into a path shows as a count on the row it calls (`◇ 3 tests`), not as a tree. The paths screen lists the changes no test reaches, even indirectly, and the changed test files with what they cover.
- **Changed types and constants are steps too.** Their impact goes through the functions using them, so a changed type sits in its path below those functions, and its path is walked up from them.
- **Changed test files are grouped by package on the paths screen:** Go test files sit under a header for their folder, since a package is the unit a Go reviewer thinks in; other languages (Rust) list one row per file. A flat list got long on big changes (#15).
- **Files can be left out with `vim.g.trail_ignore`:** gitignore-style patterns, matched by the engine (`gix::glob`) before anything else is computed, so an ignored file has no hunks, nodes, call edges or paths. A pattern that matches a folder hides everything under it. Go and Rust lockfiles, generated code and the root `vendor/` and `target/` folders are hidden by default (`vim.g.trail_ignore_defaults = false` opts out); the defaults live in the engine so other clients get them too, and `vendor/` and `target/` are anchored to the root so a package with that name deeper down stays visible. The paths screen counts the hidden files, and the engine returns their names as `ignored`, so nothing disappears silently. Hidden files are not context nodes in paths, even when reviewed code calls into them. A key to hide a file during a review, and a `.trailignore` file in the repository, are later.
- **A path can be marked reviewed by hand (`mr`):** it marks every hunk of the path's steps as seen, the same state scrolling past them sets, rather than keeping a separate flag per path. Progress is per function, so the same functions show as done in every other path that contains them, and unmarking clears them there too. A step you were on shows `▶` instead of `✓` in the tree, as before.
- **A hunk can be marked reviewed by hand (`mh`, #46):** in the diff, on the hunk under the cursor or every hunk a visual selection touches, marking them all or, when they all are already, unmarking them. It sets the same seen state as scrolling and `mr`, so steps, paths and other paths sharing the function follow. Rows of a seen hunk get a `▎` in the column between the gutter and the code, which the gutter already left blank, so the width doesn't change.
  - **Scrolling still marks hunks seen by default,** so nothing changes for anyone who doesn't use `mh`; `vim.g.trail_seen_on_scroll = false` leaves marking to `mh` and `mr`.
  - **A hunk unmarked by hand (`mh` or `mr`) is not marked again until it has left the screen.** Otherwise the next cursor move would mark it again while it was still in view. Kept in memory only, not in the review file.
- **`]s` walks the tree and climbs back out of a finished branch.** Going forward, `]s` goes to the next change down the tree, and when that change is outside the branch just finished it stops first at the row the two share, then goes on: `OriginKMSLite` (last under `ParseMaterialOrigin`), then `Activities.CreateTenant`, then `logActivityInfo`. Siblings follow each other directly, and a finished tree climbs back to its entry point. The stop is on a row already seen, to put the next branch back in context; `[s` still goes to the previous step. It goes through every step, reviewed or not: scrolling a whole file marks its other functions reviewed, so skipping reviewed steps would skip most of a new file.
- **Going to a function lands on its first change.** A step, `<CR>` on a tree row and `]]` put the cursor on the function's first hunk, on the side its lines are (the removed line when there is one, as `]c` does), and from the function's first line when the hunk starts above it, as in a new file. The line goes a few rows below the top rather than the middle, so as much of the change shows as fits. `[[` on a removed line now finds its function by the old lines, which it couldn't before.
- **`]c` / `[c` move through a path's changes:** between `]s` (a whole step) and `]h` (every hunk of the file shown, including hunks of other functions, stopping at the end of the file), `]c` goes to the next hunk that belongs to one of the path's steps and crosses into the next step when the current one has none left. It lands on the first line of the hunk, the removed line when there is one (#27).
- **The overview explains itself (#45):** it was too hard to tell what was going on. It now reads top down: the pull request (number, title, author, base) or the branch range, one progress bar over every hunk with the submit status, the description folded, "Needs attention" (counts only, each line opening what it counts), and the paths as name, bar and done/total, with threads only when there are some. Tests, hunks in no path and hidden files fold to one line each. Dropped: the summary line, the key hints (`? keys` at the bottom instead), each path's size, reach and packages (the path view shows them), and the preview tree of the selected path. CI status is left for #44.
- **Every hunk lands somewhere:** in a step of a path, in a changed test file, or under "Not in any path" (imports, package-level variables nothing uses, removed functions whose hunk no step covers).
- **Comments are written in a floating box, not a one-line prompt:** comments are often more than a sentence, and `vim.ui.input` can't hold several lines or change the kind. The box opens under the cursor, `<C-s>` saves, `<Tab>` cycles the kind, and `cc` opens it on a default kind (`vim.g.trail_default_comment_kind`, blocking if unset) so the common case is one key.
- **A comment can cover several lines:** `cc`, `cb`, `cq` and `cn` also work in visual mode. The comment stores its first line, its text and a `last` line number, on one side only: the side of the first selected line, so a selection across a removed and an added line comments on the side it started on. It shows under its last line, `ce` and `cd` work from any line of it, and it still finds its first line by text after new commits, keeping its length.
- **Saved comments sit on a faint tint of their kind's colour:** the kind colour mixed 14% into the background, padded to the comment's longest line, so a comment reads as one block apart from the code without competing with the changed tokens.
- **Reviews are submitted to GitHub as one review (`P`, #43):** an overall comment and verdict written in the comment box (`<Tab>` cycles comment, approve, request changes, draft), and every comment not sent before, as inline comments with their kind as a bold prefix. GitHub only takes inline comments on lines in its own diff, which differs from trail's (trail drops whitespace-only hunks and can comment on any line of the whole file), so the engine asks GitHub for the pull request's hunks and lists comments outside them at the end of the overall comment instead of failing. Sent comments are marked so a later submit leaves them out, and the commit submitted at is kept for reviewing only newer commits later (#40). The engine runs `gh api`, like the rest of the pull request work.
- **A pull request's review threads show in trail (#38):** under their line, in a neutral colour with each comment's author and date, read-only. Every thread takes one line in the diff (`● alice: first words…  · 3 comments`, or `✓ resolved · …`), and `<CR>` opens the whole thread in a popup below it, where `r` replies: threads written out in full made the code hard to follow; outdated ones (no line in the current code) appear only in the thread list (`T`), with the code they were written on. `]t` / `[t` move between the threads of a path's steps, and path rows count them. Threads come from GitHub's GraphQL API, the only one that says whether a thread is resolved or outdated, read when the review opens, after submitting, and on `R`.
- **Comment text is cleaned up for reading:** the carriage returns GitHub sends are dropped, the `**nit:**` prefix trail puts on submitted comments shows as a coloured kind tag, and thread and comment text wraps at 80 columns. A sent comment that a thread already holds (sent before #57 handed sent comments over) is dropped once threads load, so it isn't shown twice.
- **Replies go out at once (`r`, #39):** `r` on a thread's line, or on its row in the thread list, opens the comment box; `<Tab>` switches between reply and resolve (reopen for a resolved thread), and any text written is posted as a reply. A reply is posted right away, like GitHub's "add single comment", rather than held for `P`: it belongs to a discussion already under way, and holding it would only delay it. Uses GraphQL mutations on the thread id trail already has, then reads the threads again.
- **Once on GitHub, a comment is a GitHub thread and only that.** After `P`, a comment posted inline is dropped from trail's comments, and its thread takes its place, so a discussion lives in one place and replies (#39) go there. A comment that went into the overall comment is not a thread, so it stays, marked sent.
- **`:Trail` alone picks a pull request (#41):** it lists the open pull requests with `gh pr list`, in the repository so the host comes from its remote, and puts those asking for your review first (a second `gh pr list --search review-requested:@me`). The list goes through `vim.ui.select`, so a picker plugin the user has takes over.
- **Comments:** kinds are blocking, question and nit. For now the review is copied as markdown and pasted into an agent conversation. Sending to an agent or posting to GitHub comes later.
- **AI reviewer (later):** a fresh agent session per review, never the one that wrote the code, reused for every question in that review. It must support Claude Code and pi.

## Diff

- **difftastic, drawn by trail:** the engine runs `difft --display json` and the plugin draws the result in its own buffers. Comments on lines are essential, so difftastic's read-only terminal output was not an option. Without `difft`, a line diff with whitespace ignored is used.
- **Unchanged code is one colour:** syntax and tree-sitter highlighting are off in diff buffers, so the changed tokens are the only colour on screen. Syntax colours competed with them and made the diff noisy. The filetype is still set. Because a user's config can turn tree-sitter or semantic tokens back on afterwards, every line also gets a whole-line `TrailContext` highlight (the `Normal` text colour) above those and below the changed tokens.
- **What counts as changed:** difftastic decides. Hunks that are only formatting are dropped from the review.
- **Markers, not tinted lines:** changed lines get a `+` or `-` in the gutter, and only the changed tokens are highlighted. The tokens are drawn in colour (bold green or red text), not on a coloured background, as difftastic does: a background made a wholly new function look like a solid block.
- **Unified by default:** `t` switches to side by side and `o` toggles between folded and whole-file views. Both choices carry over to the next file.

## Navigation

- **A path showed as lanes (#82), now replaced by the tree below:** a path's changes are listed one per row, in the order `]s` walks them, with the calls between them drawn in a narrow gutter on the left, like the commit graphs of jj, lazygit and tig, and the unchanged functions between them left out. Each row has a mark (`▶` shown now, `●` reviewed, `○` not yet, `◇` an unchanged entry point), the name, and the thread count, the one column kept: a package column and an XRay-style table of state and hunks seen were mocked up, and threads chosen. `hjkl` were Vim motions there, `<CR>` showed the row's function, and the cursor followed `]s`. Tried before and dropped, because they hid most of a path: a route line (one chain from an entry point down, #80), then numbered routes with `route 2 of 15` (#81), which on a real path with an entry calling fifteen changes showed two at a time. Also mocked up and not chosen: cards per path, a three-column view of callers and callees, a call hierarchy panel and a graph centred on one function. The paths screen folds each path to one line and `za` unfolds it, the path last reviewed starting open, since fifteen rows per path would bury the rest.
- **The tree took the lanes' place, with their marks and less noise.** The tree read better for reviewing, since it shows the unchanged code a change goes through, but each row carried two marks (`✚`/`●` for the kind of change and `✓`/`▶` for review), tags (`step 4 · modified · via Store`), a package column, a `▸ N functions` row per link and `↑ joins above` rows. Now:
  - one mark per row, the lanes' review state (`▶` shown now, `●` reviewed, `○` not yet, `◇` unchanged), and the kind of change in the name's colour (green added, red removed, plain modified, dim unchanged);
  - the unchanged functions between two changes drawn in the connector (`├┄`, with `┄2` after the name), opened by `za` or `a`;
  - the step, change, interface (`via Store`), tests and package only for the cursor row, at its end;
  - a change reached again repeating under each caller, as in the lanes, instead of a join row;
  - a branch whose changes are all reviewed, none of them shown now, folded to one row (`● Activities.CreateTenant  ✓ 6 changes`), so the tree shrinks as the review goes; `za` opens one and `zR` opens everything;
  - the thread count in a column on the right, the one column the lanes kept.

  `gt` is gone with the lanes. The paths screen unfolds a path into the same tree.
- **A change reached again shows again under each caller, with the changes below it.** When a change already in the tree is also called from another change or entry point of the path (`Controller.Create` calling `ParseMaterialOrigin`, first shown under `Activities.CreateTenant`), it shows again under that caller, looking like any other row, and the changes below it repeat too, so the rows under each function read like its code. Repeated rows are never steps: `]s` and the cursor go to where a change first shows, the mark says whether it was reviewed, and `<CR>` shows its function. More than 5 changes below a repeated row fold into `▸ N changes`, which `<CR>` opens, so a big path doesn't double; a branch stops at a change already above it, so a cycle doesn't repeat. Entry points that only reach changes shown elsewhere fold into one `▸ N more entry points` row, which `<CR>` opens. This replaced listing the other callers dimmed beside a row (`⇠ Refresh, Run`), which said less and ran off the screen on changes with many callers. Considered and left out: a marker on repeated rows (`↑`), and repeated rows with nothing below them, which hid the changes a call leads to.
- **`gm` draws a path as a map of boxes, in a float:** callers above what they call, each change once under the first caller to reach it, children centred under their parent so no edges cross; the function shown and its direct callers and callees stand out and the rest is dimmed, the feature graphterm's study found people valued most. It is laid out in Lua, without `ascii-dag` or another crate, since each change is placed once, under the first caller to reach it. It is for seeing a path's shape now and then, not for working in, so it opens on a key and closes on `<CR>`, which shows the box's function.
- **`<C-p>` finds a changed function (`finder.lua`):** with a hundred steps, moving step by step is too slow to reach a function known by name. The finder lists the steps of every path once each, the path shown now first, with their review mark and the paths holding them, and opens the one picked in the path shown when it is there, otherwise the first. Only changed functions are listed, to keep the list short; `K` and `gd` cover the rest. The plugin hands the list to `vim.ui.select`, like the pull request picker, so the user's picker takes over; the app loads no plugins, so it draws its own: a prompt float and a list under it, matched with Neovim's `matchfuzzy()`, no dependency. Threads (`#`) and files (`/`) in the same box were considered and left for when jumping by function isn't enough.
- **`K` without an LSP:** the popup finds a definition with tree-sitter and `git grep`, at base on removed lines and at head elsewhere, so it works without a language server.
- **`gd` opens a separate Neovim:** the definition opens in a fresh `nvim` inside a large floating terminal, at the line, with the user's own config. `:q` returns to the diff. Two earlier attempts failed:
  - A floating buffer in the review's Neovim: pickers behind `gr` jump into a normal window, which was the review.
  - A tab per definition (#7): tabs piled up and jumps still depended on the user's config.

  The separate Neovim runs without `$NVIM`, so plugins that hand files to a parent Neovim leave the review alone. It also maps `<Esc>` in the terminal buffer, so a global "leave terminal mode" mapping doesn't swallow it, and skips swap files. Removed lines still open read-only in a float, since there is no file to edit.
- **`?` shows a screen's keys grouped, paired and short (#60):** a flat list sorted by key split pairs like `]c` and `[c` apart and read badly. Each screen has a short table of groups (Move, Review, View…) and labels; keys sharing a group and label share a line (`]s [s  step`, `cb cq cn  as kind`), in two columns when there is room. The popup still starts from the keys actually mapped on the buffer, so it never lists one that isn't there, and a mapped key missing from the table shows under Other with its description rather than disappearing.
- **trail runs as its own app on Neovim, not as a new TUI (#66):** a standalone TUI or web UI would have had to rebuild Vim motions, editing and the language server integration; mockups of both are on the design canvas. `trail` instead runs `nvim -u app/init.lua` under `NVIM_APPNAME=trail`: none of the user's config or plugins load (which also avoids #47 and #30), the layout is the tree on the left, the diff, and threads in a pane on the right instead of a popup, with the screens in the tabline and the mode and keys in a global status line. Side by side needs the width, so there the tree moves to a strip across the top (at most 8 rows, scrolled to the current step) and the thread pane to the bottom; hiding the tree was considered, but a strip keeps the path in view. The comment box opens in the same pane rather than floating over the code, so the code stays in view and can be scrolled while writing; a comment being written holds the pane until it is saved or cancelled. The app copies the user's colors by starting their own Neovim headless and reading every highlight group once their config has run, rather than loading their colorscheme by name, which would lose the options and overrides set in their config; it costs that Neovim's startup time, capped at 3 seconds. The headless Neovim fires UIEnter itself and reads the colors only once no colorscheme has been applied for 150 ms, since configs apply theirs late (LazyVim's VeryLazy waits for UIEnter, a theme switcher used `vim.defer_fn`); the app asks again on FocusGained to follow theme switches. In the app, the user's comments and GitHub threads look and act the same: a gutter mark and a hint at the end of the line instead of blocks under it, which pushed the code apart, and the pane as the one place to read them, showing a line's thread with the user's unsent comments under it. Replies there are drafts sent with the review instead of posted at once, and comments are selected for sending by default (`s` takes one out), so `S` sends everything added unless told otherwise. A list of the file's threads in the pane between threads was mocked up and not chosen. The plugin keeps comments as blocks under their lines. Sizes the user gives the tree and pane are kept per place (tree left or top, pane right or bottom): a window no longer at the size trail last set was resized by the user, checked only on WinResized, once a layout has settled, since trail's own moves resize the other windows midway and checking then, or when a window closed, took those sizes for the user's. A terminal resize resets the baseline instead of counting as the user's.
- **Calls are marked where they are made.** The engine keeps the lines of each call on the path's edges (`lines`: from the language server's `fromRanges`, or tree-sitter when matching by name), and the diff shows `→ VerifyHash · step 2` on a calling line and `← called by Login line 9` on the called function. `]]` follows the call on the line into the function it calls and `[[` goes back, or up to the caller; this follows the graph where `]s` follows the path's order, which flattens its branches. `<C-]>`/`<C-t>` and `>`/`<` were considered; `]]`/`[[` was chosen, and `h`/`l` stay Vim's.
- **Reviewing some commits narrows the range, not the review.** The Commits screen picks one commit or a run of them, contiguous so the review is still one diff (`first^..last`); any set of commits was considered and left out, since combining non-adjacent commits can conflict. The review keeps its key, so comments and reviewed hunks carry across ranges. It opens on all commits, not on those since the last submitted review. Submitting sends comments against the pull request's head, and the engine finds each comment's line again by its text there (removed lines at the merge base), which also covers commits pushed after the review loaded; a line the head no longer has goes to the review's body.
- **A step shows its function in its whole file, the rest dimmed.** Folding everything outside the function was mocked up next to dimming it, and dimming chosen: the code around stays in view for context without competing with the function. Changed tokens in the dimmed code keep their green or red, faded the same way, so a new file still reads as new around the step; fading them to the plain dim colour made new code look unchanged. `o` folds the dimmed code away; the choice is kept for the next step, apart from the hunk folding other diffs use. With no review named, the app opens on its own pull request screen rather than `vim.ui.select`, which without the user's picker plugins is a bare prompt shown only once listing finishes; a number typed while listing picks once the list arrives (a thread opened meanwhile pops up as in the plugin), then the pane shows again what it showed before, refreshed when threads reload after a reply. `gd` clears `NVIM_APPNAME` (or restores the user's own) so definitions open in the user's Neovim. `--my-config` runs the user's Neovim with `:Trail` instead. The plugin is unchanged inside the user's editor and shares review state with the app.
- **A comment can be posted at once.** `<C-s>` keeps a comment or reply for the review, `<C-y>` posts it now: a reply to its thread, a new comment as a single comment on its line (the engine's `post_comment`, finding the line again by its text like submitting). A comment GitHub refuses, on a line outside its diff, is kept for the review instead so its text is not lost. `<C-s>` keeping and `<C-y>` posting was chosen over the reverse and over a toggle in the box's title. With no review named, the app opens on its own pull request screen rather than `vim.ui.select`, which without the user's picker plugins is a bare prompt shown only once listing finishes; a number typed while listing picks once the list arrives (a thread opened meanwhile pops up as in the plugin), then the pane shows again what it showed before, refreshed when threads reload after a reply. `gd` clears `NVIM_APPNAME` (or restores the user's own) so definitions open in the user's Neovim. `--my-config` runs the user's Neovim with `:Trail` instead. The plugin is unchanged inside the user's editor and shares review state with the app.
- **One review tab:** the paths screen, a path and the send screen take turns in a single tab. Going back cancels any diff still loading for that window.

## Engine

- **Rust, JSON-RPC over stdio:** a long-lived `trail serve` process, so the plugin stays thin and other clients can reuse it.
- **The impact walk uses the language server's call hierarchy.** Tested on a small Go module with gopls: incoming calls on a concrete method include callers that only go through an interface or a method value, and with two implementations each gets only the calls that could reach it. Outgoing calls stop at the interface method, so the walk asks for its implementations to continue down. Whether a caller goes through an interface comes from asking for the definition at the call site. Without a language server the walk matches calls by name with tree-sitter and marks them uncertain; on chi that was slower (67 s against 38 s) and joined unrelated changes through every `ServeHTTP` and `String` method, so the language server is the real path and names only a fallback.
  - **The walk goes through every interface, the standard library's included.** Go code calls through interfaces everywhere, so stopping at them would hide real impact. Tried and dropped: stopping the walk at interfaces declared outside the repository (`http.Handler`), which cut chi's `Context.Reset` from 233 functions to 87 but hid callers the reviewer wants to be able to reach. The size is handled by what the view shows by default instead.
  - **Interfaces from outside the repository don't join paths.** Calls through `io.Writer` or `http.Handler` are walked and shown, labeled with the interface, but they connect nearly everything in an HTTP codebase, so they don't merge separate changes into one path. The repository's own interfaces do join paths, since services usually call their stores through one.
  - **Entry points are functions nothing outside test files calls**, so a library's public API counts. A function literal (a closure) counts as part of the function holding it: a call made inside it is a call from that function, and it is never a node of its own. gopls v0.24 reports such calls this way and name matching always did; the closure item older gopls reports is mapped to its enclosing function, so the tree is the same with any of them. A separate row per closure, which would tell several closures in one function apart, is left for later (#54).
  - **A changed file the build leaves out** (a `//go:build` line) is skipped by the language server instead of sending the whole language to name matching.
- **The language server can be turned off (`vim.g.trail_lsp = false`, #48):** the plugin sends it as `lsp` on `impact`, which then matches calls by name without starting gopls or rust-analyzer. `open` already leaves the language server out by default, since the impact walk is what asks it, so the plugin doesn't send `lsp` there. Other clients keep the defaults when they leave `lsp` out.
- **The engine owns the language servers** (gopls, rust-analyzer) and runs them in the review worktree. Calls found by name matching show at once as uncertain (`?`). The language server confirms them in the background, and the screens update when it does.
- **Go and Rust first.**
- **Stable ids:** hunk ids hash the file and the changed lines, not line numbers, so reviewed hunks stay reviewed when the author pushes again. Comments store their line's text to find it again.
- **One review worktree per repository:** reused across reviews, so build caches and language server indexes stay warm. The user's checkout is used directly when it is already at the head commit.
- **git:** reading uses gitoxide. Worktrees and pull-request fetches still call the `git` command; replacing them is issue #1.
- **Review state** (seen hunks, positions, comments, verdict) lives in `.git/trail/<review>.json`, separate from anything the engine can recompute.

## How we work

- **Track gaps as issues:** known gaps and deferred work go into GitHub issues on the repo so they aren't forgotten.
- **Branches and PRs:** one branch and PR per feature or fix, merged when the owner says so. PR text is written to sound human.
- **Tests:** a bug fix starts with a test that fails without it. Engine tests drive the binary over stdio on temporary git repos (`cd engine && cargo test`). The plugin test runs headless (`nvim --headless -u NONE -l test/plugin.lua`).
- **Real sessions:** behavior that headless Neovim can't show, like terminal mode or the tab bar, is checked in a real Neovim session in tmux before calling it done.
